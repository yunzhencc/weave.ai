# 代码审查与 PR 处理

审查或处理 PR 时读取本文；通用协作与验证要求见 [AGENTS.md](../AGENTS.md)，目录职责与依赖约束见 [架构说明](architecture.md)。

## 分开判断需求与实现

- 分别给出需求价值和实现质量的结论。实现不合格不等于需求没有价值，需求有价值也不等于当前代码可以合并。
- 根据项目方向、用户场景和现有能力判断需求。只有上下文不足以确定需求价值、且会影响处理方式时才询问用户，同时继续不依赖答案的实现质量审查。
- 作者身份、疑似 AI 生成、改动文件多或代码量大，不是拒绝需求的理由；重复代码和批量修改可以作为重点复核当前实现的信号。

## 实现质量检查

- 追踪实际调用方和数据流，检查正确性、边界输入、错误处理与回归风险，避免只检查 PR 描述中的路径。
- 核对浏览器与服务端边界、密钥处理、鉴权、任务幂等和付费请求的不确定结果；不将共享 API 令牌视为用户权限体系。
- 检查改动是否限定在需求范围内，是否包含无关文件、重复实现、不必要抽象，以及是否复用现有结构和依赖。
- 核对测试与文档是否覆盖实际行为，区分模拟上游、构建、浏览器验证和真实模型调用；检查与实际目标分支的冲突，不假设目标分支一定叫 `main`。
- 发现问题时说明触发条件、影响及具体代码位置；将可复现问题、待验证风险与风格建议分开，不把猜测写成事实。

## 处理结论

- 需求有价值但实现不合格时，保留需求，给出修正当前实现、提取可用思路后重做或记录待办的建议；创建外部 issue 或向作者发送反馈须有明确授权。
- 建议关闭 PR 时，先说明需求价值、实现质量、可保留的思路和建议处理方式；批量处理也要让用户能看清每项需求是否保留。
- 审查结论包含已验证的内容和实际限制；未发现问题不等于已完成运行验证。

## 授权与执行

- 在授权范围内完成只读审查、可逆修复和必要验证，先交出可审阅的结果，再请求尚未授权的最后一步外部动作。
- 合并、关闭 PR、推送和 force-push 均须有明确授权；执行前说明相关改动、验证结果、冲突和影响，不覆盖他人改动。
- 已有明确授权时不重复询问；若范围或影响发生实质变化，再确认新增部分。
- “提交代码”表示范围明确的本地提交，不自动推送、合并、关闭 PR 或发布版本。
